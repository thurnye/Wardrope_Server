# Wardrope Security Requirements

Security is a release requirement, not a later hardening phase. Every feature must preserve these boundaries.

## Trust boundaries

### Browser

The browser is untrusted. It may send user-controlled text, files, headers, identifiers and URLs.

The browser may receive only public configuration and sanitized application data. It must never receive:

- AWS access keys or privileged S3 credentials
- MongoDB connection strings or credentials
- AI-provider API keys
- weather-provider secret keys
- signing secrets, encryption keys or server session secrets
- internal stack traces or raw provider errors

### Wardrope API

The API is the only browser-facing trusted application boundary. It is responsible for authentication, authorization, validation, rate limits, CSRF defenses, safe error handling and use-case orchestration.

### External providers

AWS, AI, weather and other third-party providers are server-side integrations. Provider-specific payloads and errors must be normalized before crossing into Core or API responses.

## Authentication and session rules

When authentication is implemented:

- prefer short-lived server-managed sessions or short-lived tokens transported in `HttpOnly`, `Secure` cookies;
- do not store long-lived bearer tokens in `localStorage` or `sessionStorage`;
- set an explicit `SameSite` policy appropriate to the deployment topology;
- rotate session identifiers at login and privilege changes;
- invalidate server-side sessions on logout, password reset and security-sensitive account changes;
- rate-limit login, password-reset, verification and recovery endpoints separately from the general API limit;
- prevent user enumeration in authentication and recovery responses;
- hash passwords with a current adaptive password hashing algorithm and a reviewed work factor.

## CSRF

Credentialed cookie authentication requires CSRF protection on state-changing requests.

Wardrope will require a server-validated CSRF token for authenticated `POST`, `PUT`, `PATCH` and `DELETE` browser requests, in addition to restrictive CORS and cookie settings. CORS alone is not treated as CSRF protection.

## Authorization

Authentication is not authorization.

Every user-owned resource must verify ownership server-side before read, update, delete, upload attachment, recommendation access or history access. Client-supplied user IDs are never trusted as proof of ownership.

## Image uploads

The only supported image flow is:

```text
Browser -> Wardrope API -> validation/processing -> private S3 -> MongoDB reference
```

The frontend never writes directly to S3.

Upload requirements:

- require authentication and ownership authorization;
- enforce route-specific file count and byte limits before processing;
- validate the real file signature in addition to extension and declared MIME type;
- allowlist supported image formats;
- decode and validate dimensions to block decompression/image bombs;
- re-encode accepted images and strip unnecessary metadata where appropriate;
- generate server-side randomized object keys rather than trusting filenames;
- store objects privately and return only controlled application references;
- use least-privilege S3 permissions and encryption at rest;
- keep S3 and MongoDB state consistent when one side of the operation fails;
- never execute or serve an uploaded file as active content.

## Request handling

- request IDs are either generated by Wardrope or accepted only from a strict safe-character allowlist;
- JSON and form bodies have explicit size limits;
- endpoints use focused schema validation and reject unknown/invalid data where appropriate;
- query filters, sorting and pagination are allowlisted rather than passed directly to MongoDB;
- database identifiers are parsed and validated before use;
- user-controlled values are never interpolated into shell commands or server file paths.

## Responses and logging

- production API responses never contain stack traces, provider messages, connection strings or secret values;
- production logs do not blindly serialize request bodies, cookies, authorization headers or arbitrary provider exceptions;
- security-sensitive events should include a request/correlation ID without logging sensitive payloads;
- errors returned to users are stable application error codes with safe messages.

## Network and deployment

- production uses HTTPS only;
- `TRUST_PROXY_HOPS` must match the real trusted reverse-proxy topology and must not be guessed;
- production CORS origins are explicit and cannot default to localhost;
- security headers are enabled centrally with Helmet;
- rate limits are centrally enabled; distributed deployments must move rate-limit state to shared infrastructure before horizontal scaling;
- MongoDB and S3 are not publicly writable from the browser.

## Dependency and CI policy

- Node.js uses the chosen LTS baseline from `.nvmrc`;
- CI must type-check, test, build and audit production dependencies;
- GitHub Actions are pinned to reviewed commit SHAs;
- once a verified npm lockfile is generated, CI switches from `npm install` to `npm ci`;
- high-severity production dependency audit findings block completion until reviewed and resolved.

## Feature completion checklist

A security-sensitive feature is incomplete until its happy path and meaningful abuse/failure paths are tested. Examples include unauthorized access, wrong-owner access, invalid payloads, oversized uploads, unsupported files, expired sessions, invalid CSRF tokens, provider failures and persistence failures.
